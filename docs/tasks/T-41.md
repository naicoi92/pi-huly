## Vấn đề

`src/tools/domains/issues-core.ts:96-101` — `parseMarkupSafe(f.description)`
fail vì `f.description` runtime là **object-id string** dạng
`<issue-_id>-description-<epoch>`, KHÔNG phải inline markup string. Fallback
trả nguyên chuỗi id → LLM thấy id vô nghĩa.

```ts
const descMarkup = parseMarkupSafe(f.description);
const descMd = descMarkup !== null ? markupToMd(descMarkup as never) : f.description;
//                                                                    ^^^^^^^^^^^^^
// fallback = raw field value, ở đây là object-id string
```

Huly lưu issue `description` dạng **reference tới một Document object** riêng
(description document), KHÔNG phải inline markup string. Client return field
`description` = serialized object-id string
`"<owner-id>-description-<timestamp>"`. `parseMarkupSafe` trên chuỗi đó →
`null` (không phải valid markup JSON) → fallback return nguyên chuỗi id.

`get_document` (`findOne(DOCUMENT_CLASS, { _id: <id> })`) → not found vì id đó
không phải `document:class:Document` chuẩn (class khác / lookup path khác).

## Phương án (sau T-44 confirm storage model)

1. **Preferred**: `get_issue` tự resolve description document inline — lookup
   đúng class + _id, markupToMd, return markdown content. Một round-trip thêm
   nhưng UX đúng.
2. **Fallback**: nếu description là ref string pattern `<id>-description-<ts>`,
   return `description: null` + field `descriptionDocumentId` rõ ràng + doc tool
   support lookup class đó.

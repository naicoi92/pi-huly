## Vấn đề

Khi WS tới Huly transactor gặp error (connection refused, timeout, server down,
token expired, reconnect), upstream
`@hcengineering/client-resources@0.7.423/lib/connection.js:554` in ra stderr:

```js
wsocket.onerror = () => {
  ...
  console.error("client websocket error:", socketId, this.url, this.workspace, this.user);
};
```

Chuỗi user thấy: `client websocket error: 1 wss://huly.ltt.onl/_transactor/<api-token> ...`

**Hai vấn đề**:

1. **Spam break UI** — WS error có thể lặp lại mỗi lần reconnect (backoff),
   tràn ngập stderr, che lấp log pi-huly (T-56 tool call log). User báo "đừng
   cho nó spam màn hình nữa".
2. **Token leak (security)** — `this.url` chứa `_transactor/<api-token>`. Token
   bị in ra stderr/UI. Vi phạm NFR-04 (no-leak). Nếu log được capture/export
   (CI, log aggregator) → **token compromise**.

### Root cause đã verify (Phase 1 investigation)

- **File nguồn**: `node_modules/.pnpm/@hcengineering+client-resources@0.7.423/
  node_modules/@hcengineering/client-resources/lib/connection.js:554`
- **`client-resources` là transitive dep** — KHÔNG có trong `package.json`
  `dependencies` của pi-huly (chỉ có api-client/core/platform/text-core/text-markdown).
  Được resolve qua Huly plugin loader khi `connect()` initialize model handler.
- **Upstream KHÔNG expose seam** — không có `MeasureContext`/log-level injection
  ở `ClientSocket`/`ClientConnection`. Giống T-62.
- **Cùng file có 7+ dòng spam khác** (cùng root cause class):
  - `:82` `console.log("Generate new SessionId", sessionId)` — session info
  - `:139` `console.log("no ping response from server. Closing socket.", ...)`
  - `:286` `console.log("Connected to server:", serverVersion)` — version info
  - `:329` `console.error("unknown response id: ...")` — protocol error
  - `:373, :402` `console.log("Processing upgrade", ...)` — upgrade info
  - `:488, :496, :510, :518` `console.error(err)` — decompress/data error
  - `:641` `console.error("measure slow findAll", ...)` — perf warning
- **Tất cả break UI**, không có seam upstream.

## Phương án (đăng ký pattern vào filter framework T-62 + KHÔNG spam)

T-64 KHÔNG xây cơ chế filter riêng — **dùng filter framework T-62**
(`runWithConsoleFilter` + pattern registry). T-64 chỉ **đăng ký thêm pattern**
vào `DEFAULT_UPSTREAM_NOISE_PATTERNS` + verify token leak được filter.

Bounds:
- **KHÔNG spam màn hình** (user yêu cầu rõ) — filter toàn bộ dòng WS error +
  spam khác, KHÔNG redact giữ URL. **Filter = không log ra**.
- **Đăng ký pattern** vào `DEFAULT_UPSTREAM_NOISE_PATTERNS` (T-62):
  - `/^client websocket error/i` ← dòng chính, có URL + token
  - `/^Generate new SessionId/i`
  - `/^no ping response from server/i`
  - `/^Connected to server/i`
  - `/^unknown response id/i`
  - `/^Processing upgrade/i`
  - `/^measure slow findAll/i`
  - (decompress error `:488, :496, :510, :518` là `console.error(err)` thuần —
    KHÔNG match first-arg string pattern → cần decision: filter ALL error trong
    scope connect, HOẶC để T-62 framework hỗ trợ filter theo error shape).
- **Token leak verify** — test KHÔNG chỉ assert "filter đếm đúng" mà còn assert
  **stderr captured KHÔNG chứa `_transactor/` + KHÔNG chứa substring token**.
  Đây là security guard, KHÔNG chỉ UX.
- **KHÔNG thay đổi behavior reconnect** — filter chỉ gate log, WS onerror vẫn
  chạy backoff/reconnect logic bình thường (KHÔNG swallow error state, chỉ
  swallow log output).
- **WS error thật nghiêm trọng** (vd auth fail, server down vĩnh viễn) → tool
  call sẽ throw `ConnectionError`/`AuthError` qua `mapError()` (đã có từ T-04) →
  LLM thấy error rõ ràng qua `toToolResult`. KHÔNG bị che vì filter chỉ gate
  upstream `console.error`, KHÔNG gate error throw từ `createHulyClient`.
